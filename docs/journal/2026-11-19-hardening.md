# 2026-11-19 公開に向けて server.js を攻撃に強くする（feat/hardening）

締切 11/30 まで残り 11 日（16:22 JST に開始）。ブランチ `feat/hardening`（B7〜B9 の入った `feat/b1-b4` の上に作った。PR #3 が `main` ではなく `feat/b1-b4` に入っていて、`main` にはまだ B7〜B9 が無いため）。

## 直す前に調べた弱点（今の server.js）

AGENTS.md「DoS 対策は3層」のうち、**3 層目（アプリの制限）** を受け持つ。1・2 層目（Cloudflare・ファイアウォール）は公開のときに別に行う。

| # | 弱点 | どう悪用されるか |
|---|---|---|
| 1 | 部屋の数に上限が無い。`GET /posts?room=xxx` を開くだけで部屋ができる（サンプル 3 件入り） | 部屋名を変えながら GET を送り続けると、部屋が無限に増えてメモリを食いつぶし、サーバーが落ちる（1 部屋 200 件 × 140 字で、1 部屋あたり最大で数百 KB） |
| 2 | 回数の制限が無い（ポスト・いいね・一覧・SSE） | 1 台から連打するだけで、タイムラインを荒らす・CPU を使い切る・いいねを好きな数に増やす |
| 3 | 送られてくるデータの大きさの上限がアプリに無い（Bun の標準は 128MB）。`req.json()` で全部読む | 大きな本文を何本も送り、メモリを使わせる |
| 4 | JSON の形の確認が甘い。`name`・`text` 以外のキーがあっても通る。`Content-Type` を見ていない | 変な形のデータをそのまま受ける。`Content-Type` を見ないと、ほかのサイトから「単純なリクエスト」としても送れる |
| 5 | いいねは何回でも押せる（1 人 1 回は画面の localStorage だけで守っている） | `curl` で同じポストに何千回もいいねできる |
| 6 | SSE の接続数に上限が無い。読まない相手にも送り続ける。`server.timeout(req, 0)` で時間切れも無い | 接続を何万本も開いたままにして、メモリとファイル記述子を使い切る。読まない相手には、送る文字が溜まり続ける |
| 7 | `development: true` のまま。エラーの処理（`error`）が無い | 予想外の例外が起きると、Bun の開発用エラー画面（**スタックトレース・ファイルのパス**入り）が返る |
| 8 | セキュリティ用のヘッダが無い（`X-Content-Type-Options`・`Content-Security-Policy`・`X-Frame-Options` など） | 別のサイトの枠（iframe）に入れて押させる、ファイルの種類の取り違えなど |
| 9 | 相手の IP の取り方が決まっていない | Cloudflare の後ろでは、全員が Cloudflare の IP に見える。逆に `CF-Connecting-IP` を誰からでも信じると、ヘッダを書き換えて制限をすり抜けられる |
| 10 | CORS が `*`（どのサイトからでも fetch できる） | ほかのサイトを見た人のブラウザを使って送らせられる。2 の回数制限で抑える（公開時は `CORS_ORIGIN` で自分のドメインだけにする） |

## 直したこと
上の表の 1〜9 をすべて直した（10 は環境変数 `CORS_ORIGIN` で公開時に絞れるようにした）。中身と数は `docs/explain.md` の「公開に向けた守り」。
- 新しいファイル: `client-ip.js`（相手の IP。Cloudflare の範囲は https://www.cloudflare.com/ips-v4 ・ ips-v6 を 2026-11-19 に取得）・`rate-limit.js`（回数の制限）・`hardening.test.js`（16 件）・`scripts/loadtest.js`（負荷試験）
- 画面は Bun の HTML の読み込みをやめて、`STATIC_FILES` の表から自分で配るようにした（ヘッダを付けるため）
- 公式の答えは見ていない

## 確かめた手順と結果
1. `bun test` → **28 pass / 0 fail**（前からの 12 件 ＋ 新しい 16 件）。新しい 16 件は、上限を小さくしたサーバー（ポスト 3 回・部屋 3 つ・SSE 1 人 2 本・全体 4 本・寿命 1.5 秒）を立てて確かめる:
   - ポスト 4 回目・一覧 11 回目・同じポストへのいいね 2 回目・いいね 6 回目 → 429（`Retry-After` つき）
   - `CF-Connecting-IP` を信じない設定で、毎回違う IP を名乗っても 4 回目は 429（すり抜けられない）
   - 5000 バイト・200KB の本文 → 413（そのあとも一覧は 200）。`text/plain` → 415。余分なキー・配列・壊れた JSON → 400
   - 部屋が 4 つ目になると、いちばん使われていない部屋のポストが消える（使い直した部屋は残る）。新しい部屋 6 つ目 → 429
   - SSE 3 本目 → 429、1 本閉じるとまたつなげる。全体 5 本目 → 503。1.5 秒でサーバーから切られる
   - ない URL の 404 に `<script>` が返らない。画面と API の返事にセキュリティ用のヘッダ
2. Bun の開発用エラー画面の確かめ（例外を投げる小さなサーバーで）: `development: true` で `error` なし → **500 でスタックトレースとファイルの場所入りの 50KB**。`development: false` ＋ `error` → 決めた短い文だけ。
3. 画面: 内蔵ブラウザで 8001 番の `bun --hot server.js`（`script.js` の `API` を一時的に 8001 にし、最後に 8000 に戻した）。ポスト（Ctrl+Enter）・いいね（ピンク）・「● ライブ」がすべて動き、CSP によるエラーはコンソールに 0 件 → OK
4. 負荷試験 `bun scripts/loadtest.js`（手元の Windows。同時 50 本で各 8 秒。「毎回違う人」は `CF-Connecting-IP` で名乗り、それを信じる設定で立てた＝ IP ごとの制限が効かない、いちばん厳しい場合）。メモリは Windows の作業セット:

| 段階 | 前のサーバー（`feat/b1-b4`） | 直したサーバー |
|---|---|---|
| 起動直後 | 31 MB | 32 MB |
| flood（1 人が一覧・ポスト・いいねを連打） | 44 MB（ポスト 34,314 件・すべて受け付け） | 47 MB（受け付けたのは一覧 300・ポスト 10・いいね 1、ほかの 332,678 回は 429） |
| rooms 1 回目（違う部屋を作り続ける） | 370 MB | 55 MB |
| fill 1 回目（600 部屋に 140 字のポスト） | 392 MB | 68 MB |
| rooms 2 回目 | 557 MB | 64 MB |
| fill 2 回目 | **653 MB（増え続ける）** | **61 MB（増えない）** |
| SSE を 700 本 | 700 本すべてつながる | 500 本つながり、200 本は 503 |
| 最後（3 秒後に一覧を取る） | 200（落ちてはいない） | 200（落ちない）・63 MB |

- 前のサーバーは、部屋とポストの分だけメモリが増え続けた（このまま続ければメモリを使い切る）。直したサーバーは 55〜68 MB で頭打ちになった。

## 困ったこと
- 負荷試験の SSE の段階が終わらなかった。Bun の `fetch` は同じ相手への同時接続の数に上限があるらしく（推測。数は調べていない）、つなぎっぱなしの SSE を何百本も開けない。SSE だけ `node:net` で TCP を直接開き、HTTP を手で書いて解決した。
- 直した直後は、前のサーバーより 1 秒に答えられる数が 15 分の 1 ほどに落ちていた（rooms 1 回目で 19,106 回 対 322,089 回）。原因は 2 つ: (1) 回数の記録が 10,000 人に届くと、新しい人が来るたびに記録を全部見て古いものを探していた。記録は数えはじめた順に並び、区切りの長さも同じなので、先頭から見て「まだ新しい記録」に当たったら止めるようにした。(2) 部屋を消すたびに `console.log` していた（攻撃中は毎回）。消した。→ 117,292 回まで戻った（まだ前より少ないのは、毎回の部屋づくり・回数の記録のぶん）。
- テスト用のサーバーを止めるのに、`bun` をまとめて止めるコマンドを使おうとしたら止められた（別の作業の 8000 番の `bun --hot` まで止めてしまうため）。自分のポートを使っているプロセスだけを止めた。
- PR #3（B7〜B9）が `main` ではなく `feat/b1-b4` に入っていて、`main` には B7〜B9 が無かった。このブランチは `feat/b1-b4` の上に作ったので、この PR を `main` に入れると B7〜B9 も一緒に入る。

## 確かめていないこと
- Cloudflare を通したときに `CF-Connecting-IP` が正しく使われること（公開前なので、テストでは「同じ PC の中継を信じる」設定で代わりに確かめた）。
- Linux（本番の Ubuntu）での負荷試験。メモリの数は Windows の作業セット。
