### server.js：ポストを覚えて、頼まれたら返すサーバー

- `Bun.serve` でサーバーを 8000 番で立てる。`routes` は「URL と GET/POST の組み合わせ → どの関数が答えるか」の表。
  - `GET /` → `index.html` を配る（だから http://localhost:8000/ で画面が出る）
  - `GET /posts?room=部屋` → その部屋のポスト一覧を JSON で返す（`getPosts`）
  - `POST /posts?room=部屋` → 名前と本文を受け取り、新しいポストを作って保存（`createPost`）
  - `POST /posts/:id/like?room=部屋` → その id のポストの `likes` を 1 増やす（`likePost`）
  - `GET /posts/events?room=部屋` → つなぎっぱなしにして、変化を知らせる（SSE。B9 で使う）
- 保存場所は **メモリ**（`rooms` という Map。部屋の名前 → ポストの配列）。データベースは使っていないので、**サーバーを止めるとポストは消える**。
  - `globalThis.rooms` に置いているのは、`bun --hot` がファイル保存のたびに読み込み直しても、ポストを消さないため。
- 入力は必ず確かめる: 部屋名は `^[A-Za-z0-9-]{1,32}$`、名前 20 字・本文 140 字まで（絵文字を 1 字と数えるため `Array.from` で数える）、空は不可。だめなら 400 と理由を返す。1 部屋 200 件を超えたら古いものから消す（メモリを使いすぎないため）。
- `CORS_HEADERS` は、別の URL で開いた画面（`bun run index.html`）からの fetch も受け付けるための印。

### script.js：サーバーとやりとりして画面に並べる

- 先頭の `API`（サーバーの場所 `http://localhost:8000`）と `ROOM`（部屋の名前 `sample`）を、すべての fetch で使う。
- `showPosts()`: `GET /posts` で一覧を取り、`<template id="post-template">` の見本をコピーして 1 件ずつカードを作り、タイムラインに入れる。
  - 名前と本文は **`textContent`** で入れる（`innerHTML` だと、本文に書かれた HTML が動いてしまう＝XSS になるため）。
- `addPost()`: 名前と本文を `JSON.stringify` して `POST /posts` に送り、終わったら本文欄を空にして `showPosts()` で取り直す。
- `addLike(id)`: `POST /posts/{id}/like` を送って取り直す。
- 「ポストする」ボタン → `addPost`、更新ボタン → `showPosts`。ページを開いたときにも 1 回 `showPosts()`。

### なぜ「いちばん下に足す」のか
- CSS は、同じ強さの指定が 2 つあると **後に書いたほうが勝つ**。もとの `.post` や `.avatar` を消さずに、いちばん下に上書きを足したので、「何を変えたか」が 1 か所にまとまって読みやすい。
- 例外: マウスを乗せたときの `.post:hover` は `.post` より強い（クラス＋`:hover`）ので、下に足した `.post` の白い背景を上書きしてしまう。もとの色は透明なので、灰色の下地が透けてカードが灰色になった。そこで `.post:hover` も下に足し、`color-mix` で「白に紫を 4% 混ぜた色」にした。

### `--accent`（CSS 変数）を変えると何が変わるか
- `var(--accent)` を使っている所（ポストするボタン・更新ボタンの文字・名前の入力欄・「さらに表示」・投稿欄のアイコン）が、1 行の変更で全部紫になる。色を 1 か所で決めておく利点。

## 応用ミッション B1〜B4：投稿欄と自動更新（`script.js`・`index.html`・`styles.css`・`server.test.js`）

公式の答え（`advanced/`）は見ていない。手元資料 DOCS.md のヒントだけを使った。1 つのブランチ `feat/b1-b4` にまとめ、コミットはミッションごとに分けた（4 つとも `script.js` と投稿欄の同じ場所を触るので、別々のブランチだと PR どうしがぶつかるため）。

### B1 残りの文字数（`updateCharCount`・`countChars`）
- 本文の欄に `input` イベント（1 文字打つたび・消すたびに起きる）を付け、`140 - 文字数` を `#char-count` に入れる。
- 文字数は `Array.from(text).length` で数える。`text.length` だと絵文字（😀）を 2 字と数えてしまい、サーバー（`server.js` も `Array.from`）と数がずれるため。
- 0 より小さくなったら `over` クラスを付けて赤くし（`classList.toggle`）、ポストするボタンを `disabled` にする。`addPost` の中でも 140 字を超えたら送らない（ボタンを使わない Ctrl+Enter でも止めるため）。
- 最後の守りはサーバー。画面のチェックは「使いやすさ」のため、サーバーのチェックは「守る」ため（ブラウザを使わず curl で送られても断れる）。

### B2 ポストした時刻（`formatTime`）
- サーバーはポストを作るときに `createdAt`（ISO 形式の時刻の文字。例 `2026-11-19T07:02:21.000Z`）を付けている。それを `new Date()` で時刻にし、今との差を分で出す。
- 1 分未満「たった今」、1 時間未満「N分前」、1 日未満「N時間前」、それより前は「11/19 16:02」。
- 投稿カードの見本に `<time class="time">` を足し、`textContent` で入れる。`title` に日付と秒までの時刻を入れたので、マウスを乗せると正確な時刻が出る。
- 「3分前」は時間がたつと古くなるが、B4 の 10 秒ごとの更新で描き直されるので、自然に「4分前」に変わる。

### B3 Ctrl+Enter でポスト（`postByShortcut`）
- 本文の欄に `keydown`（キーが押された）イベントを付ける。`event.key === 'Enter'` で、`event.ctrlKey`（Ctrl）か `event.metaKey`（Mac の ⌘）が押されていれば `addPost()`。
- `event.preventDefault()` で、本文に改行が入るのを止める。
- `event.isComposing` が true のとき（日本語の変換中）は何もしない。変換を決める Enter でポストされないようにするため。
- `isPosting` という印を付け、送っている途中は次のポストを送らない。キーの連打で同じポストが 2 件になるのを防ぐ（試すと、3 回続けて押しても 1 件だけだった）。`finally` で、成功しても失敗しても印を戻す。

### B4 10 秒ごとの自動更新（`showPosts`・`autoReload`・`loadPosts`）
- `setInterval(autoReload, 10 * 1000)` で 10 秒ごとに一覧を取り直す。別のタブを見ているあいだ（`document.hidden`）は画面が見えないので取りに行かない（サーバーの負担を減らす）。
- **入力中の内容が消えない理由**: 取り直しで書き換えるのは `#timeline`（タイムラインの `<ul>`）の中だけ。名前・本文の入力欄には触らない。
- **同じ通信が重ならない理由**: `isLoading` という印で、一覧を取りに行っている途中かを覚えておく。途中で頼まれたら（更新ボタンの連打、ポストの直後など）すぐには送らず `reloadAgain` に「あとでもう 1 回」と覚え、終わってから 1 回だけ取り直す。捨てずに 1 回取り直すのは、ポストした直後の頼みを捨てると、自分のポストが 10 秒間出てこないため。
  - 試すと、更新ボタンを 5 回続けて押しても、通信は 2 回（最初の 1 回＋待っていた分の 1 回）で、同時に飛んでいる通信は最大 1 本だった。
- サーバーが止まっているときは `try...catch` でエラーを受け止め、画面はそのままにする。次の 10 秒後にまた試す。
- もとの `showPosts` の中身（取ってきて並べる）は `loadPosts` に名前を変え、`showPosts` は「重ならないように呼ぶ係」にした。

### bun test（`server.test.js`）
- `beforeAll` で `bun server.js` を別のポート（8765）で立て、`fetch` で頼みごとを送って返事の番号（201・400・404）を確かめる。部屋の名前はテストごとに新しくして、ほかのポストと混ざらないようにした。
- 確かめていること: 本文 140 字は OK・141 字は 400、絵文字 140 個は OK（1 字と数える）、空白だけの本文・21 字の名前・空の名前・使えない部屋名は 400、ない id へのいいねは 404、`createdAt` が今の時刻、一覧が新しい順。
- テストが本当に効いているかを確かめるため、わざと `server.js` の上限を 141 にすると「141字は 400 で断られる」だけが落ちた（確かめたあと元に戻した）。

## 応用ミッション B7〜B9：アイコン・自分のいいね・SSE（`script.js`・`index.html`・`styles.css`・`server.js`・`server.test.js`）

公式の答え（`advanced/`）は見ていない。手元資料 DOCS.md のヒントだけを使い、ヒントと違う作り方をしたところは理由を書いた。ブランチ `feat/b7-b9`（3 つとも `script.js` の `loadPosts` を触るので 1 本にまとめた）。

### B7 人ごとに違うアイコン（`avatarColor`・`initialOf`）
- 投稿カードの見本の `<img class="avatar">` を `<div class="avatar initial">` に変え、名前の 1 文字目を `textContent` で入れる（名前はユーザーが入力した文字なので、`innerHTML` は使わない）。
- 1 文字目は `Array.from(name)[0]` で取る。ヒントの `name[0]` だと、絵文字（😀）の名前で絵文字が半分に切れて文字化けするため（B1 で文字数を数えたときと同じ理由）。
- 色は 8 色の配列から選ぶ。**ヒントとの違い**: ヒントは 1 文字目の番号で選ぶが、それだと「たろう」と「たけし」のように頭文字が同じ人がいつも同じ色になる。そこで名前の全部の文字を djb2（5381 から始め、33 を掛けて文字の番号を足す、という有名な混ぜ方）で 1 つの数にし、色の数で割った余りで選んだ。同じ名前ならいつも同じ色になる。
  - 最初は 33 ではなく 31 を掛けていたが、色の数 8 で割ると、サンプルの「たろう」と「はなこ」が同じ色になった。31 は 8 で割ると 1 足りない数（31 = 32 − 1）なので、混ざり方が弱かった。33 にすると、サンプルの 3 人が 3 色に分かれた。
  - 8 色しかないので、別の名前が同じ色になることはある（避けられない）。
- 色は白い太字が読める濃さのものを選んだ（ヒントの黄色 `#ffad1f` などは白い文字が読みにくいので使っていない）。

### B8 自分がいいねしたハートをピンクに（`likedIds`・`loadLikedIds`・`saveLikedIds`・`showLiked`・`addLike`）
- 押したポストの id を `Set`（同じものを 2 回入れない入れ物）にためる。カードを作るとき `likedIds.has(post.id)` なら `liked` クラスを付け、CSS でハートと数をピンク・ハートを塗りつぶしにする。
- **ブラウザに保存する方法**: `localStorage` に、`minix-liked-部屋の名前` という名前で、id の配列を JSON の文字にして保存する（`JSON.stringify`）。ページを開いたときに読み出す（`JSON.parse`）。
- **なぜブラウザに保存するのか**:
  - このミニX にはログインがなく、サーバーは「誰が」いいねしたかを知らない（`likes` は数だけ）。だから「自分が」を覚えられるのは、自分のブラウザだけ。
  - 変数に入れるだけだと、再読み込みで消える（お題は消えてもよいが、B9 で画面がよく描き直されるようになったので、消えないほうが自然）。`localStorage` は再読み込みしても、ブラウザを閉じても残る。
  - 部屋ごとに名前を分けたのは、別の部屋のポストの id と混ざらないようにするため。
  - 限界: 別のブラウザ・別の PC・シークレットモードでは、ピンクにならない。ブラウザの記録を消すと戻る。サーバーは数えるだけなので、記録を消せばもう一度いいねできてしまう（1 人 1 回を本当に守るにはログインが要る）。
- 保存がない・壊れている・保存を許されていない（シークレットモードなど）ときは `try...catch` で受け止め、空から始める。配列の中も文字だけを使う（ほかの物が混ざっていたら捨てる）。
- **1 人 1 回**: いいね済みのハートは押しても何も送らない（サーバーにはいいねを取り消す口がないので、押すたびに増えるより自然）。押したら返事を待たずに先にピンクにし、連打しても 2 回目は送らない（試すと、3 回続けて押しても +1 だけだった）。届かなかったら（サーバーが止まっている・ポストが消えた）記録を戻す。
- サーバーから消えたポスト（1 部屋 200 件を超えた古いもの）の id は、一覧を取るたびに記録からも消す（`forgetDeletedLikes`）。記録がいつまでも増えないようにするため。

### B9 更新ボタンなしで、すぐ届く（SSE。`connectEvents`・`onEventsOpen`・`onEventsError`・`autoReload`）
- `new EventSource(API + '/posts/events?room=' + ROOM)` でサーバーの知らせの口につなぐ。誰かがポストやいいねをすると、サーバーが `data: changed` を送ってくるので、`message` イベントで `showPosts()` を呼んで取り直す。
- **B4（10 秒ごとの取り直し）と二重にならない整理**: `isLive`（SSE がつながっているか）を持ち、`autoReload` は `isLive` のあいだは何もしない。つまり 10 秒ごとの取り直しは「SSE が切れているあいだの予備」になる。試すと、つながっているあいだの 25 秒間、取り直しは 0 回だった。
  - 知らせが続けて来ても、B4 で作った `isLoading`・`reloadAgain` の仕組みで、同時に飛ぶ通信は 1 本にまとまる。
  - ポストやいいねをしたあとの `showPosts()` は残した。SSE の知らせでも取り直すので 1 回多くなることがあるが、SSE がこっそり切れていても自分のポストは必ず出るほうを選んだ。
- **切れたら自動でつなぎ直す**:
  - サーバーが止まった・ネットが切れたときは、ブラウザ（EventSource）が自分でつなぎ直してくれる（`readyState` が CONNECTING）。間隔はサーバーがつないだときに送る `retry: 3000`（3 秒）。
  - サーバーがエラーの返事をしたときなどは、ブラウザが諦める（`readyState` が CLOSED）。そのときだけ、自分で `setTimeout` でつなぎ直す。待ち時間は 1 秒から倍々にし、最大 30 秒（サーバーが落ちているときに、何度も頼んで負担をかけないため）。
  - つながったら（つなぎ直せたときも）1 回取り直す。切れていたあいだのポストを取りこぼさないため。
  - ヘッダーに「● ライブ」（緑）／「つなぎ直し中…」（灰色）を出し、今どちらで更新しているかが見えるようにした。
- **サーバー側で変えたこと**（`server.js`）:
  - つないだときに `retry: 3000` を送る（上のつなぎ直しの間隔）。
  - 30 秒ごとに全部の接続へ `: ping`（`:` で始まる行はコメントで、ブラウザは知らせとして扱わない）を送る。公開するときに通す Cloudflare などの中継は、しばらく何も流れない接続を切ってしまうため。`bun --hot` で読み込み直すたびにタイマーが増えないよう、`globalThis` に置いて前のものを止めてから作る。
  - もう切れている接続に送ると例外になるので、`sendEvent` の中で `try...catch` し、その接続を取り除く（`removeListener`）。
- `bun test` に、SSE につなぐと `retry: 3000` が届き、ポストといいねのたびに `data: changed` が届くことを確かめるテストを足した（12 件すべて通る）。

## 公開に向けた守り（feat/hardening。`server.js`・`client-ip.js`・`rate-limit.js`）

公開すると、誰でも（プログラムでも）連打できる。AGENTS.md の「DoS 対策は3層」のうち、**3 層目のアプリの制限** をここで受け持つ。1 層目（Cloudflare の保護）と 2 層目（オリジンには Cloudflare 経由でしか来られないようにする）は、公開の作業で別に行う。直す前に調べた弱点は `docs/journal/2026-11-19-hardening.md` にある。公式の答えは見ていない。

上限の数は `server.js` の先頭の `LIMITS` にまとめた（環境変数 `MINIX_...` で変えられる。テストで小さな上限を試すため）。

| 守り | どこ | 何をするか |
|---|---|---|
| 部屋の数の上限 | `openRoom`・`touchRoom` | 部屋は 500 まで。超えたら **いちばん長く使われていない部屋** を消す。`Map` は入れた順を覚えるので、使うたびに入れ直すと、先頭が「いちばん使われていない部屋」になる。1 人が 1 分に新しく作れる部屋も 10 まで（作り続けて、ほかの人の部屋を押し出すのを防ぐ）。いいねでは部屋を作らない |
| 回数の制限 | `rate-limit.js`・`checkLimit` | 1 人（IP）ごとに 1 分あたり: ポスト 10・いいね 60・一覧 300・SSE のつなぎ直し 30。超えたら **429** と `Retry-After`（何秒待てばよいか）。断られたポストも 1 回と数える |
| いいねの連打 | `likePost` の `sameLike` | 同じ人が同じポストにいいねできるのは 10 秒に 1 回 |
| 相手の IP | `client-ip.js` の `clientIp` | ふつうは接続してきた相手の IP。`CF-Connecting-IP` ヘッダは、**Cloudflare の IP の範囲から来たときだけ** 信じる（誰でも書けるヘッダなので、ほかから来たものを信じると、IP を名乗り放題になり制限をすり抜けられる）。同じサーバーの中継（Cloudflare Tunnel など）を使うときだけ `MINIX_TRUST_LOCAL_PROXY=1` |
| IPv6 | `client-ip.js` の `ipKey` | IPv6 は 1 つの回線に /64（前半 4 区切り）がまとめて配られ、後半は自由に変えられる。前半 4 区切りで 1 人と数える |
| 覚える人の数 | `rate-limit.js` | 回数の記録も 1 つの制限につき 10,000 人まで。超えたら古い記録から消す（記録そのものでメモリを食いつぶされないため） |
| データの大きさ | `readJsonBody`・`maxRequestBodySize` | ポストの JSON は 4096 バイトまで（**413**）。`Content-Length` を見て読む前に断り、読んだあとも測る。どの URL でも 64KB を超える本文は Bun が読む前に断る |
| JSON の形 | `readJsonBody`・`checkPostBody` | `Content-Type: application/json` でなければ **415**。中身はふつうのオブジェクトで、キーは `name` と `text` の 2 つだけ（`likes` などを混ぜたら 400） |
| SSE の接続数 | `getEvents` | 全体で 500 本（超えたら **503**）、1 人 20 本（超えたら 429）。閉じたら数を戻す（`removeListener` は 2 回呼ばれても数がずれない） |
| 無通信・読まない接続 | `sendHeartbeats`・`sendEvent` | 1 本は最長 10 分で切る（ブラウザは 3 秒後に自動でつなぎ直すので、ふつうの人は困らない。黙って消えた相手の接続が残り続けない）。読まずに送る文字が 32 個溜まった接続も切る。ふつうの接続は 10 秒何も来なければ切る（`idleTimeout`。少しずつ送ってつなぎっぱなしにする攻撃を防ぐ） |
| エラーの中身 | `development: false`・`serverError` | 思いがけない例外では「サーバーで問題が起きました」だけを返し、中身はサーバーの記録にだけ出す。試すと、前の設定（`development: true`・`error` なし）では **スタックトレースとファイルの場所入りの 50KB の画面** が返っていた。404 も、送られた URL をそのまま返さない |
| セキュリティ用のヘッダ | `SECURITY_HEADERS`・`withHeaders` | `X-Content-Type-Options: nosniff`（種類を推測させない）・`X-Frame-Options: DENY` と CSP の `frame-ancestors 'none'`（ほかのサイトの枠に入れさせない）・`Content-Security-Policy`（画面が読み込めるのはこのサーバーのファイルだけ。もし XSS があっても、よそのスクリプトは動かない）・`Referrer-Policy`・`Permissions-Policy` |
| 画面のファイル | `STATIC_FILES`・`serveStatic` | Bun の HTML の読み込み（`import index from './index.html'`）ではヘッダを足せないので、`index.html`・`script.js`（B6 からは `script.ts` を JavaScript に直して）・`styles.css`・`icon.svg` を表に書いて自分で配るようにした。毎回ファイルを見るので、書き換えたら再読み込みだけで届く |

**公開するときの設定**（環境変数）: `HOST=127.0.0.1`（中継からだけ受ける）・`CORS_ORIGIN=https://公開する URL`・`CSP_CONNECT_SRC=`（同じ URL なら `'self'` だけで足りる）・Cloudflare Tunnel を使うなら `MINIX_TRUST_LOCAL_PROXY=1`。

**防げないもの**（正直に書く）: たくさんの IP からの攻撃（DDoS）はアプリでは止められない（1・2 層目の Cloudflare の仕事）。IP ごとの制限なので、同じ IP の教室や会社では、みんなで 1 人分の上限を分け合う（上限は多めにした）。ポストはメモリにしか無いので、サーバーを止めると消える。部屋が 500 を超えると、使われていない部屋は消える。

**確かめ方**: `bun test`（`hardening.test.js` が上限を小さくしたサーバーで 429・413・415・503 などを確かめる）。`bun scripts/loadtest.js` で手元で連打して、メモリが増え続けないことを見る（前のサーバーとの比べは journal）。

## 応用ミッション B6：本体を TypeScript にする（`server.ts`・`script.ts`・`client-ip.ts`・`rate-limit.ts`・テスト）

参考にしたのは DOCS.md の B6 のヒント（`as HTMLInputElement`・`type Post`・`String(post.likes)`）。答えの `script.ts` は写していない（答えは昔の短い script.js 向けで、今のコードとは別物）。

- **動きは変えていない**。足したのは型だけ。`bun test`（30 件）と画面の手順（journal）で前と同じに動くことを確かめた。
- **型の検査**: `bunx tsc`（`tsconfig.json`）。`strict`（null かもしれない値や、型の書いていない引数をエラーにする）と、使っていない変数をエラーにする設定にした。Bun は型を見ずに動かすので、型の間違いは `tsc` でしか見つからない。
- **ポストの形** `type Post = { id; name; text; likes; createdAt }` を、`server.ts` と `script.ts` の両方に書いた（画面とサーバーで同じ形）。
- **画面の部品を探す** `byId<T>(id)`・`part<T>(card, selector)`（`script.ts`）: `getElementById` は「見つからないかもしれない（null）」型を返すので、毎回 `as HTMLInputElement` と書く代わりに、1 か所で「無ければエラーにする」関数にまとめた。`<T>` は「何の部品として受け取るか」を呼ぶ側が決める印（ジェネリクス）。
- **分からない形のデータ**: `JSON.parse` の結果は `unknown`（何が入っているか分からない）として受け、`checkPostBody` で 1 つずつ確かめてから `PostInput` として使う。`any` は使っていない。
- **`declare global`**（`server.ts`）: `bun --hot` で読み込み直してもポストが消えないよう `globalThis.rooms` に置いている（B9 まで同じ）。TypeScript に「globalThis にこの名前・この型のものがある」と教える書き方。
- **部屋の名前の確かめ方を 1 つにまとめた** `readRoom(req)`: 4 つの API で同じ 4 行を書いていたので、TS にするときに関数にした。よければ部屋の名前（文字）、だめなら 400 の返事（`Response`）を返し、呼ぶ側は `instanceof Response` で見分ける。
- **ブラウザは .ts を読めない**: `server.ts` の `serveStatic` が、`/script.ts` を頼まれたら `Bun.Transpiler` で型を取り除いて JavaScript にしてから配る（`toJavaScript`）。結果はファイルの更新時刻といっしょに覚えておき、書き換わったときだけ直し直す（毎回直すと CPU を使うため）。前もって `.js` を作る手順（ビルド）は要らない。
  - `bun run index.html` で開いたときは、Bun の開発用サーバーが自分で .ts を読むので、これも動く。
- **`script.ts` の最後の `export {}`**: これが無いと、TypeScript は中の名前（`API` など）を全ファイル共通の名前として扱い、`server.ts` と同じ名前がぶつかったことにする。「このファイルはモジュール」という印。
- **API の場所**: 前は「https なら画面と同じ場所、http なら localhost:8000」だった。今は「ふだんは画面と同じ場所、`bun run index.html`（3000 番）のときだけ localhost:8000」。`bun server.ts` が画面も API も配るので、同じ場所にするほうが単純で、8000 番以外で動かしても動く（確かめるときに 8000 番が別のサーバーに使われていて困ったのがきっかけ）。
- **`server.js` を 1 行だけ残した**: 本番の systemd は `bun server.js` で起動している。設定を変えずに更新できるよう、`server.js` は `import './server.ts'` だけにした。
- 足した道具（`package.json` の `devDependencies`）: `typescript`（型の検査）と `@types/bun`（Bun の型）。どちらも検査のためだけで、サーバーを動かすときには要らない（本番では `bun install` しなくてよい）。
